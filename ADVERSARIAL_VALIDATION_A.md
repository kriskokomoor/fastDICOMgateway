## 2. Validation 1 — fixture and method

**Transfer syntax:** Explicit VR Little Endian (`1.2.840.10008.1.2.1`).

**Canary:** `NESTED_SQ_CANARY_VALIDATION_A1_DO_NOT_PERSIST` — unique to this experiment, distinct
from every M1–M5 canary and self-marking as synthetic.

**Fixture (`build_validation1_fixture`):** file preamble + `DICM` + File Meta (declaring Explicit
VR LE) + a dataset containing:

- `Modality (0008,0060)` = `OT` (ordinary field, untouched by policy — sanity anchor)
- **Controls**, all at the top level, exactly the tags/behavior the fixed policy targets:
  `PatientName (0010,0010)` = `VALIDATION_A_TOPLEVEL_CONTROL^SYNTHETIC`,
  `PatientID (0010,0020)` = `VALIDATION-A-TOPLEVEL-CONTROL-ID`,
  `PatientBirthDate (0010,0030)` = `20990101`, one private element
  `(0019,0010)` = `VALIDATION_A_PRIVATE_CONTROL`.
- **The test case:** `Other Patient IDs Sequence (0010,1002)`, VR `SQ`, one Item, containing a
  nested `PatientID (0010,0020)` = the canary above.
- `Pixel Data (7FE0,0010)` — 256 deterministic bytes, untouched by policy (sanity anchor).

Method: (a) read the fixture with `fastdicomstructure.read_buffer()` directly, read-only, purely to
confirm the fixture itself is well-formed and the nested element is structurally present *before*
touching the gateway; (b) call `fastdicom_gateway.transform.process(source_bytes)` — the actual
production entry point, unmodified; (c) inspect `output_bytes` three independent ways: literal byte
search, a second `fastdicomstructure.read_buffer()` reparse, and an independent `pydicom.dcmread()`.

## 5. Validation 2 — fixture and method

**Transfer syntax:** Implicit VR Little Endian (`1.2.840.10008.1.2`).

**Canary:** `NESTED_SQ_CANARY_VALIDATION_A2_DO_NOT_PERSIST` — unique to this experiment.

**Fixture (`build_validation2_fixture`):** file preamble + `DICM` + File Meta (declaring Implicit
VR LE) + a dataset containing:

- `Modality (0008,0060)` = `OT` (implicit-encoded, ordinary field).
- **Condition B, the mutation trigger:** top-level `PatientName (0010,0010)` =
  `VALIDATION_A_TOPLEVEL_CONTROL^SYNTHETIC`, implicit-encoded — a tag the fixed policy will erase.
- **Condition A, the test case:** `Other Patient IDs Sequence (0010,1002)` encoded with Implicit
  VR's tag+length-only header, where the declared length equals the byte size of a hand-built Item
  (`FFFE,E000` + length + a nested implicit-encoded `PatientID (0010,0020)` = the canary) — i.e. a
  **defined-length** nested sequence, matching exactly the construction
  `fastDICOMstructure/tests/integration/test_parse_implicit_vr_le.cpp`'s own "defined-length nested
  sequence is NOT expanded" test uses (`wrap_in_item` + `element_implicit_header` with the item's
  own size as the declared length), reproduced independently here rather than reused from that test
  file.

No Pixel Data / private element was added — the mutation trigger and the test case are sufficient
and this keeps the fixture minimal, matching the existing repository's own minimal-fixture style
for Implicit VR scenarios (`build_unmodified_implicit_vr_fixture`).

Method: identical in spirit to Validation 1 — (a) read-only pre-transform inspection with
`fastdicomstructure.read_buffer()` to observe diagnostics and structural classification, (b) call
`transform.process(source_bytes)` (the actual production entry point), (c) inspect `output_bytes`
via literal byte search, a fastDICOMstructure reparse, and an independent pydicom parse.

## 6. Validation 2 — observed result

From `publication_validation/adversarial_validation_a_results.json` (`validation2`):

| Check | Result |
|---|---|
| Initial parse succeeds | **True** |
| Diagnostics for the defined-length sequence | **None** — `pretransform_diagnostics = []`, `pretransform_blocking_diagnostic_count = 0` |
| Sequence represented structurally or as opaque value | **Opaque** — `pretransform_sequence_is_sequence = False`, `pretransform_sequence_vr = "UNKNOWN"`, 62-byte opaque value confirmed (by direct byte search) to contain the canary |
| `pretransform_is_modified` (before policy runs) | `False`, as expected |
| Unrelated top-level policy mutation occurs | **True** — `elements_touched = 1` (the top-level `PatientName`), `private_elements_removed = 0` (none present) |
| Serialization succeeds (does NOT hit the Unsupported/500 path) | **True** — `transform_process_succeeded = True`, `transform_process_error = null` |
| Nested targeted canary survives in `output_bytes` (literal bytes) | **True** |
| Output transfer syntax | `1.2.840.10008.1.2.1` (Explicit VR LE) — confirms the modified-Implicit-VR-input-always-writes-Explicit-VR-output behavior documented in `roundtrip-contract.md` |
| Output reparses cleanly with fastDICOMstructure | **True** |
| fastDICOMstructure's own reparse of the output's `(0010,1002)` element | Still opaque — `is_sequence=False`, `vr="UN"` (i.e. the writer re-emitted it as an explicit `UN`-VR element, still unexpanded) |
| Output parses with pydicom | **True** |
| pydicom's own interpretation of `(0010,1002)` in the output | **`VR="SQ"`** — pydicom's own data dictionary recognizes `(0010,1002)` as a known Sequence tag and, per its own UN-element re-interpretation logic, automatically re-parses the raw `UN` bytes as a Sequence |
| pydicom, once re-interpreted as SQ, observes the nested value | **True** — `pydicom_nested_patient_id_values_if_expanded_as_sq = ["NESTED_SQ_CANARY_VALIDATION_A2_DO_NOT_PERSIST"]` |
| `pydicom_canary_observed_by_any_means` | **True** |

An unanticipated but directly relevant nuance surfaced by this experiment: fastDICOMstructure's own
reparse still reports the element as an opaque `UN`-VR value (consistent with the library never
claiming to expand it), but **pydicom — an ordinary, off-the-shelf DICOM toolkit — automatically
reconstructs the nested Sequence/Item/PatientID structure from the same bytes**, because pydicom's
data dictionary knows `(0010,1002)` is normally `SQ` and applies its own UN-to-known-VR
re-interpretation. This means the surviving canary is not merely present as an opaque byte string a
human would have to decode by hand — a standard downstream DICOM viewer or toolkit consuming the
object from durable storage would recover it as a clean, structured `PatientID` value with no
special effort.

## 7. Validation 2 — disposition

**HYPOTHESIS CONFIRMED**, in full, including every specific mechanical step hypothesized:

- the defined-length sequence is parsed as an opaque value — confirmed;
- no diagnostic identifies that opacity as policy-relevant — confirmed (zero diagnostics of any
  severity);
- an unrelated top-level policy mutation makes `Structure.is_modified()` true — confirmed
  (`elements_touched=1` from the `PatientName` erase);
- `write_bytes()` therefore succeeds rather than following the unmodified-Implicit-VR
  `Unsupported`/500 path — confirmed;
- output is emitted as Explicit VR — confirmed;
- the opaque nested source bytes pass through unchanged and are recoverable (both as raw bytes and,
  via pydicom's dictionary-aware re-interpretation, as a clean structured value) — confirmed.

## 8. Exact implications for the current article claims

**Does the §5 policy table require a scope qualifier?**
Yes, in the narrow sense that the table's "remove" / "replace with `DEMO`" rows for
PatientName/PatientID/PatientBirthDate are now experimentally confirmed to apply only to
occurrences of those tags at the top level of the dataset — not to occurrences nested inside a
sequence item, under either Explicit or Implicit VR. The "Private elements | remove" row is *not*
affected by Validation 1 (private-element removal is separately confirmed nesting-aware by source
inspection in `ADVERSARIAL_CLAIM_CLOSURE.md` Question A, and neither experiment here contradicts
that), but *is* affected by Validation 2 insofar as a private element hidden inside an
Implicit-VR opaque defined-length blob would be just as invisible to `erase_private()` as the
patient tag was — because there is no `Sequence`/`Item` structure for the nesting-aware traversal to
recurse into, regardless of which mutation is being applied.

**Does §8's "removes exactly what policy says to remove" require narrowing?**
Yes. That sentence is now experimentally shown to be true only for the top-level occurrences the
fixed policy actually inspects; it is not true if a targeted tag occurs nested inside a sequence
(Explicit VR, confirmed by Validation 1) or inside an Implicit-VR defined-length blob (confirmed by
Validation 2, with the added, empirically-observed twist that the surviving value is trivially
recoverable via an ordinary DICOM toolkit's own dictionary-based reinterpretation, not just present
as inert bytes).

**Does the article need an Explicit-VR-vs-Implicit-VR limitation?**
Partially, and the two experiments point to two different scopes. The **nested-tag gap
(Validation 1)** is not Implicit-VR-specific — it occurs under ordinary Explicit VR, with no
malformed or unusual encoding involved, and is arguably the more important finding for an article
whose demonstration fixtures are entirely Explicit VR. The **opaque-blob gap (Validation 2)** is
specifically an Implicit VR phenomenon layered on top of the same top-level-only mechanism. A
single Explicit-VR-vs-Implicit-VR framing would understate Validation 1's result, which needs no
Implicit VR involvement at all.

**Does anything in these results invalidate the demonstrated transform-before-persist
architecture itself?**
No. Both experiments confirm the architectural ordering claim rather than contradict it:
`transform.process()` still completes parse → policy → serialize → verify before any bytes exist to
send anywhere, and in both experiments the object that *would* be submitted for durable persistence
is exactly, and only, `result.output_bytes` — precisely what the load-bearing sentence in §5
describes. What these results narrow is a different claim: the *completeness* of the fixed
demonstration policy's coverage (which occurrences of a targeted tag it actually reaches), not
*where in the pipeline* policy runs relative to persistence. The architecture correctly enforces
"only the policy's output crosses the boundary"; it does not, on its own, guarantee that the fixed
demonstration policy's three named tags find every occurrence of themselves in an arbitrary input
object — a distinction the article's existing claims/nonclaims framing already gestures at ("nothing
close to a full de-identification profile") but does not currently make this specific.
